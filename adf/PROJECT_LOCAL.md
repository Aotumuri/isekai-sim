# プロジェクト内 ADF の設計とロードマップ

## 現行コードから確認した原因

- `.agents/skills` は旧 `agents/tools/research.py` を起動し、Desktop は `adf/sessions.py` と SQLite で別に状態遷移を管理していた。直近の対策は管理スレッドから旧 Skill を隠し、共有ロックで競合を防ぐものだった。
- `adf/store.py` が Application Support を既定にし、`service.py` の登録・権限検査は ADF 自身を含むリポジトリの登録を拒んでいた。監督の DB に関する復旧をエージェントに任せると、公式サンドボックスの境界で止まる。DB の所有は監督に一本化する。
- AppKit が `desktop_bridge.py` 経由で監督に接続していた。画面更新に再ビルドが必要で、結果不明の操作に対する Core の照合をすべて GUI から実行できなかった。
- `.git` は Codex プロファイルで読み取り専用。人間の差分確認とコミットを維持し、監督に Git 書き込みを委譲しない。

## 構成

- 各チェックアウトの `adf/runtime/` に運用 TOML、SQLite、実験、IPC、保全コピーを置く。単一監督とプロジェクト行で既存の主キー・外部キーを保持する。クライアントに登録・切替操作を公開しない。
- CLI、Web、Skill から同じ監督の操作を呼ぶ。Web は数値ループバックの個別ポートで動かし、閉じても監督を終了しない。Codex と GitHub は既存の App Server と gh アダプターを利用する。
- GitHub が課題の正本。SQLite の実行用の課題 ID と照合情報は GitHub の Issue に結び付ける。実験待機、利用枠確認、停止世代の検査はプログラムが処理する。
- 通常の Codex スレッドでの Skill 利用は読み取り・相談と、人間への管理セッション起動手順の提示に限る。公開 RPC は管理下の保存済みスレッドを ID で再開できる。外部クライアントの実行中スレッドの所有権や起床は保証できない。 [公式 App Server](https://learn.chatgpt.com/docs/app-server)
- 管理ロールの公式プロファイルで ADF 本体と運用状態への書き込みを拒否し、運用状態の読み取りも拒否する。Web とファイル IPC は OS ユーザーを信頼する。外部スレッドには同じプロファイルを強制できない。

## 段階と判定

| 段階 | 優先する変更と判定 |
| --- | --- |
| A | ローカル監督、統一 CLI・Skill、停止と世代管理、旧状態のプレビュー・保全・選択取り込み。隔離テストで二つのチェックアウトが同時に動き、クラッシュ後の再開と実験通知の重複防止を確認する。 |
| B | ビルド不要の Web、会話・停止・承認・結果照合、Mission/範囲、運用モード。模擬 Codex と GitHub で全経路を確認し、公式認証・制限と権限境界を実環境で確認してから研究運用へ移る。 |
| C | Program と研究品質（分類別報告、否定的結果、独立レビュー）、内部メッセージと起床条件、研究報告の全文検索、任意の意味検索、時間帯・予算配分、スレッド方針、権限付き Worker/Reviewer。既存履歴を保ち、重複起床と複数書き手を抑え、外部 API は明示承認後のみ利用する。 |
| D | 対話導入、既定の Snapshot に加えて Working Tree・Worktree 実験、資源上限、保持ポリシー、ホスト枠、他 OS、更新元と署名・自動更新・復元。停止中の整合性検査と復元試験が通り、重要成果物の保全を確認してから有効にする。 |

C・D は既存機構を維持しながら段階導入する。研究課題の生成には Mission、既存・失敗課題の照合、起票と着手の独立した承認が必要。Research Autonomous の受け入れでは有意義な候補のない場合の停止、既存課題の選択と次の仮説への継続を別々に確認する。
