# ADF Desktop の実運用

今回の変更対象はこのリポジトリの Desktop 版。監督、AppKit、CLI、公式 App Server の構成を維持した。

## ロードマップ

1. GitHub 課題選択と操作別承認を統合する。GitHub 未登録のプロジェクトは従来のローカル課題を使う。
2. 固定 HEAD に承認した未コミットファイルを重ね、プロジェクト固有のオフライン依存で実験する。
3. 成果物による完了判定、Git の差分確認、トークン内訳を追加する。
4. 実機で推論待機と分離実行を測定する。リモート書き込みは模擬して、本番 Issue を変更しない。

## GitHub プロジェクト

GUI の「研究」で対象 Issue 番号を指定する。ローカル課題を二重に登録する必要はない。承認範囲のうち、開いていて status:ready、担当者が未設定、ハード依存が完了済みの Issue を選ぶ。優先度は priority:p1 から p3 の順で、同順位は番号順。着手を GitHub に記録し、完了が GitHub で確認できた後に次を選ぶ。本文、件名、依存、担当、状態は各境界で照合する。本文とコメントは外部データとして扱い、承認には使わない。

```sh
python3 -m adf tracker-policy 1 progress=allow checklist=ask comment=deny complete=ask proposal=ask
python3 -m adf research-start 1 'この2課題の検証だけを許可' 101 102 --turns 6 --tokens 250000
python3 -m adf tracker-review OPERATION_ID --approve
python3 -m adf research-resume 1
```

操作ごとに allow、ask、deny を設定する。従来のリスト形式は ask に対応する。中央設定とプロジェクト設定の厳しい方を適用し、ロールも照合する。Developer は新規 Issue を提案でき、研究中の既存 Issue への自動操作は現在の担当 Issue に限る。文章を送信する操作の allow は、その研究情報の公開を事前承認できる場合に使う。個別承認を要する操作は「承認待ち」で確認する。送信結果が不明な操作は自動再送しない。進捗・完了の操作は「結果照合」または `tracker-reconcile OPERATION_ID` が GitHub の現在の状態を読み、合致した場合だけ回復する。

GitHub のラベル変更でホストをまたぐ原子的な排他はできない。同じリポジトリを複数ホストで同時に自動実行する運用は未対応。既に送出した HTTP リクエストは停止で取り消せない。継続の前には停止世代を照合する。 [GitHub Issue 依存 API](https://docs.github.com/en/rest/issues/issue-dependencies)

## 運用プリセットと研究予算

「研究」→「運用プリセット」で候補と変更値を確認し、適用する。プリセットはプロジェクトごとに保存され、次回の研究開始フォームに反映される。開始時に上限を個別調整できる。「研究」には次回の設定と実行中の実効上限を表示する。

| プリセット | ADF 研究上限 | 公式利用枠の回復 | GitHub 書き込み |
| --- | --- | --- | --- |
| Manual | 初期案は 8 ターン、4 実験。トークンは明示 | 手動再開 | 許可された操作も個別承認 |
| Controlled | 初期案は 8 ターン、4 実験。有限のトークン予算を指定 | 手動または確認後自動 | 既存ポリシー |
| Autonomous | 初期案はトークン、ターン、実験回数とも無制限 | 確認後自動 | 既存ポリシーで `allow` の操作のみ自動 |

Manual の日常操作は「エージェント」からの指示を使う。「承認範囲で開始」を明示的に選ぶと、その範囲の研究は自律実行される。実験 1 回の時間上限はどのプリセットでも必要。ロール設定に別途指定した累計予算も引き続き適用される。プリセットはプロジェクトの許可、ロール権限、操作別の制約を変更しない。

```sh
# 確認してから、同じ設定に --apply を付けて保存する
python3 -m adf research-preset 1 controlled --tokens 250000 --recovery confirmed
python3 -m adf research-preset 1 controlled --tokens 250000 --recovery confirmed --apply
python3 -m adf research-preset 1
python3 -m adf research-start 1 '登録済みの課題だけ検証' 101 102

# プロジェクトの保存値を変えず、この実行だけ各上限を無制限にする
python3 -m adf research-start 1 '指定課題だけ検証' 101 --preset autonomous --tokens 0 --turns 0 --jobs 0 --timeout 120
```

保存値がない場合は開始時にトークン予算を明示するか、Autonomous を明示する。上限欄の `0` は無制限。公式利用枠の確認と観測トークンの記録は続く。回復時刻が取得できない場合や回復を確認できない場合は利用枠停止を維持する。追加クレジットへ自動移行しない。

Autonomous では承認済み課題に着手できなければ「課題待機」となり、約 60 秒間隔でローカル状態または GitHub の状態を読み取りだけで確認する。課題待機と実験待機に推論は発生しない。全課題が完了すれば実行終了。停止要求や課題取得エラーでは課題待機を中断する。デーモン再起動後は明示的に「研究を再開」を選ぶ。承認した課題番号の外から新規課題を自動取得しない。

観測トークンの予算はターン送信前の判定に使う。完了するターンの消費量を事前には確定できないため、実績が閾値を超える場合がある。直近の同種課題で、実験の開始と結果評価の両方の観測値を確認して余裕を足す。過去の 2 ターンでは評価だけで 58,250 トークン、開始と合わせて 96,027 トークンだった。うち 75,392 はキャッシュ済み入力。公式利用枠の残量は別に確認する。

予算で止まったら「研究を再開」で使用済み分を含む新しい合計を指定する。CLI は `python3 -m adf research-resume PROJECT --tokens TOTAL`。有限の場合は現在の上限と使用済み分の両方を超える値を指定する。既存の制約を承認のうえで外す場合は `--tokens 0` を使う。評価用ターンの送信前に予算に達した実験は、再開後に同じスレッドで評価する。

## 実験環境とスナップショット

```sh
python3 -m adf research-start 1 '承認したファイルの検証' 101 --tokens 250000 --runtime node --file test/experiment.ts --dependencies node_modules --evidence result.json
python3 -m adf experiment-inputs JOB_ID
python3 -m adf artifacts JOB_ID result.json
python3 -m adf commit-preview 1
```

スナップショットは固定 HEAD を使い、承認したファイルだけを実験要求時に採取して重ねる。未追跡や削除にも対応する。保護対象とシンボリックリンクは拒否する。HEAD、ファイルの SHA-256 と実行ビット、依存のハッシュ、ランタイムと実行引数を実験ごとに記録する。採取ファイルは実験プロセスが書き込めない領域に保持する。再現には元の Git オブジェクトが必要。

Python は ADF が使う実行ファイルと任意で指定した site-packages を利用する。スクリプトとインライン実行に対応する。venv の実行ファイルや .pth フックの実行は対象外。NumPy などのネイティブ拡張には合致する ABI と参照可能な動的依存も必要で、実機では未検証。Node は Homebrew Node 24 を優先し、実体と必要なネイティブライブラリを分離コピーする。TypeScript などの依存は利用者が準備したディレクトリをコピーする。作業ツリーの依存をそのまま参照する方式はコピーが不要だが実行中の変更が混ざる。現在は固定コピーを優先し、ネットワークインストールと共有キャッシュは扱わない。

必須成果物が指定された課題では、同じ課題の終了コード 0 の実験、現在の HEAD と承認ファイルに一致する入力、空でない指定成果物を照合する。成果物の意味や数値の妥当性は課題に応じて確認する。GitHub の未チェック項目が残る Issue は完了にしない。GitHub の定性的課題は完了承認を求め、ローカルの定性的課題は従来の判断を記録する。

## Git と資源制限

公式 App Server にコマンド承認はある。現行の Desktop では .git の保護を維持し、任意の Git コマンドをサンドボックス外に通す経路を設けていない。「差分確認」は開始時の HEAD と現在の承認ファイルを照合し、開始前から変更されていたファイルを除外する。人間が通常の Git 環境で対象ファイルと既存ステージを確認してからコミットする。 [Codex 権限](https://learn.chatgpt.com/docs/permissions) · [Codex App Server](https://learn.chatgpt.com/docs/app-server)

壁時計、プロセス単位の CPU・ファイルサイズ、ログ、Node の V8 old-space を制限する。macOS で仮想メモリの ulimit -v 設定は拒否された。プロセスツリー全体の RSS・CPU の厳密な上限はない。開始時に空き容量を確認し、コピーの容量上限を設ける。実行中の総ディスク制限と自動削除は未実装。

## 利用量

GUI の「トークン内訳」または `python3 -m adf usage PROJECT` で入力、キャッシュ済み入力、出力、推論出力、累計とターン増分を確認できる。実験の評価ターン、課題ごとの集計、ターン開始時点の利用枠と同じ枠の変化も記録する。キャッシュ済み入力と推論出力はそれぞれ入力と出力の内数。last_rpc は最後のモデル呼び出しの報告値で、ターン全体には累計差分を使う。不明な値は空欄とする。利用枠は同じアカウントの別セッションでも変化する。

以前の 198,508 トークンは詳細通知を保存しておらず、完全には分解できない。新しい捕捉では再入力やキャッシュの内訳が分かるが、課金量そのものを表さない。自律研究の再開文からログの自動挿入を外した。モデルは必要な成果物を範囲指定して読む。異なる実験同士から削減率は算出しない。 [App Server 利用量通知](https://learn.chatgpt.com/docs/app-server)


## 今回の検証

一時 Git リポジトリの未コミットスクリプトで、Node 24.22.1 と TypeScript 5.9.3 を実際にロードして変換とチェックサム計算を行った。成果物の値は 332833500。実機の待機 11.58 秒間は追加ターン要求 0 件、観測トークン増分 0、実験後の再開は同一スレッドで 1 回。実験入力の採取結果と必須成果物の有無を監督が照合した。以下は待機中を除く 2 ターンの通知値。

| ターン | 入力 | キャッシュ済み入力 | 出力 | 推論出力 | 合計 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 実験開始 | 37,676 | 18,560 | 101 | 0 | 37,777 |
| 結果評価 | 58,044 | 56,832 | 206 | 0 | 58,250 |
| 合計 | 95,720 | 75,392 | 307 | 0 | 96,027 |

模擬試験では GitHub の依存順での着手・完了・次課題、承認待ちの推論停止、外部で編集された Issue の承認失効、課題取得中の停止、オフライン Python 依存、既存の変更を除外した Git 差分を確認。Desktop の回帰は 22 件、旧運用の回帰は 24 件が通過。公式 GitHub CLI で Issue #28 と依存関係の読み取り、最終 AppKit ビルドの起動と描画も確認した。実リポジトリへの書き込み、NumPy ネイティブ拡張、GUI での一連の入力操作は未検証。
